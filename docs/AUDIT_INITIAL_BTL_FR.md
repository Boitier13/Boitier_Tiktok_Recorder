## 2. Phase 1 — Audit du backend réel

### 2.1 Organisation et fonctionnement du moteur

- **Interface existante :** Tkinter, fichier principal `Multi-Stream-Recorder.py`, interface concentrée dans `msr/gui.py` et les panneaux/modules `msr/*`.
- **Orchestration :** `msr/recorder.py` (`StreamRecorder`) crée un worker `multiprocessing.Process` par canal. La structure des workers est indexée par canal, avec protections contre le double démarrage, supervision et redémarrage après sortie inattendue. Le code n’impose pas un plafond produit arbitraire aux canaux enregistrés ; cela ne constitue pas une mesure de capacité maximale.
- **Détection :** polling configuré dans `msr/config.py`, valeur par défaut **3 minutes**, jitter de 20 %, erreurs avec temporisation progressive. Les workers démarrent leur vérification rapidement au démarrage. Une vérification manuelle/réveil de worker et une présence séparée pour les comptes désactivés existent dans le moteur.
- **TikTok :** `msr/worker.py` construit `https://www.tiktok.com/@<handle>/live`. La détection utilise `yt-dlp`, puis, quand celui-ci indique hors ligne, le repli `check_tiktok_live_webcast()` dans `msr/platforms.py` : API `api-live/user/room`, page profil/live pour le `roomId`, puis points Webcast US/global. Le code de téléchargement/enregistrement TikTok sélectionne Streamlink. Ces mécanismes sont présents, mais leur disponibilité dépend des changements côté TikTok, du réseau, des dépendances et parfois des cookies. Aucune requête réelle TikTok n’a été validée pendant cet audit.
- **Coupures :** fenêtre de reconnexion configurable ; le code prévoit des vérifications plus rapprochées à 15 s puis 30 s pendant la période de grâce, redémarrage supervisé de worker et traitement de certains changements de résolution.
- **Fichiers :** capture brute en `.ts`, puis remux par FFmpeg vers MP4. L’output temporaire est vérifié (présence, taille et durée lisible) avant publication. Le fichier brut est conservé en cas d’échec de remux et des fichiers restants sont repris au démarrage/nettoyage. Métadonnées JSON associées possibles. Le chemin standard est organisé sous `Recorded/<plateforme>/<créateur>` et `Processed/<plateforme>/<créateur>` ; il ne correspond pas exactement au classement date/créateur proposé dans le cahier.
- **Audio/vidéo :** le moteur conserve les flux source et remuxe sans réencodage quand possible. La synchronisation, la présence d’une piste audio et la compatibilité du MP4 doivent être mesurées sur de vrais LIVE TikTok ; elles ne sont pas démontrées par les seuls tests unitaires.
- **Bibliothèque :** `msr/library*.py`, `msr/recordings_index.py` et `msr/library_actions.py` incluent navigation, indexation, recherche/consultation, statistiques d’espace et outils de nettoyage avec mécanismes réversibles/confirmation. Il existe également un éditeur de clips, des journaux, des outils de diagnostic, et des actions sur les fichiers. La conservation de ces fonctions utiles sera décidée après vérification de leurs dépendances TikTok.
- **Notifications et arrière-plan :** notification de bureau best-effort par `plyer`, filtrage anti-répétition ; icône système avec `pystray`/Pillow lorsque disponibles ; minimisation dans la zone de notification dans l’interface existante. Les notifications ne proposent pas encore tout le contenu et les actions contextuelles souhaitées (avatar, ouverture du LIVE/dossier/fiche). Il n’y a pas de preuve d’une option d’ajout au démarrage Windows comparable à celle de la maquette front-end.
- **Paramètres et persistance :** `config.ini`, `channels.json`, fichiers d’état ; écritures atomiques, historique/restauration, protection DPAPI d’un secret Windows spécifique. Le répertoire de données est configurable (`--data-dir`/`MSR_HOME`). Les paramètres existants sont orientés Multi-Stream Recorder et devront être filtrés/présentés pour BTL.
- **Interface de contrôle existante :** `msr/control.py` et `msr_ctl.py` fournissent déjà un protocole local JSON sur TCP, lié à `127.0.0.1`, avec port dynamique et jeton généré aléatoirement conservé dans un fichier protégé. Le protocole expose commandes machine-lisibles de statut, liste de canaux, édition du roster, sessions/enregistrements, réglages, bibliothèque, journaux et événements/abonnement. Il est une piste d’adaptation importante, pas encore une API destinée au frontend Creator Radar.

### 2.2 Dépendances et vigilance pour le nettoyage TikTok

Dépendances Python principales dans `requirements.txt` : `yt-dlp[default]`, `streamlink`; recommandées : `psutil`, `curl_cffi`, `websocket-client`; options GUI : `pystray`, `Pillow`, `plyer`. FFmpeg/ffprobe est un outil externe nécessaire au remux ; Python/Tkinter sont également requis pour l’application actuelle.

Ne pas supprimer `yt-dlp`, `streamlink`, FFmpeg ou le cœur du worker comme simple conséquence de la suppression d’autres sites : les chemins TikTok les utilisent également. `curl_cffi` participe au chemin de repli réseau TikTok lorsqu’il est disponible. En revanche les fonctionnalités Twitch/Kick/YouTube/Rumble/Fishtank et leurs réglages, modules et dépendances exclusivement dédiés devront être retirés uniquement après traçage des imports et tests de non-régression. Le moteur a aussi des fonctions communes (supervision, processus, stockage, bibliothèque, clips, sécurité) à préserver.

### 2.3 Tests exécutés et limites de preuve

- Sur une extraction temporaire de `engine`, **95 tests ciblés hors dépendance à l’interface graphique ont réussi** : parseurs TikTok, reconnect, découpage/remux, présence, configuration, santé/disque et gardes temporelles.
- Une tentative plus large a buté sur l’absence de `tkinter` dans l’environnement Linux de l’audit (tests GUI et un test dépendant du module GUI) ; un test lié aux lettres de lecteurs Windows a été ignoré. Il s’agit d’une limite de l’environnement, pas d’un test Windows.
- Les tests TikTok de cette branche vérifient principalement l’extraction du `roomId` et l’interprétation de JSON d’exemple ; ils ne testent ni les réponses réseau live de TikTok, ni l’authentification/cookies, ni le succès de Streamlink, ni un enregistrement TikTok complet.
- Aucun essai réel multi-LIVE, aucune mesure CPU/RAM/bande passante/disque sur le PC de référence, aucune vérification de notification Windows et aucun test de Windows 10 n’ont pu être réalisés ici.

## 4. Architecture intégrée partiellement — validation bornée

**Ne pas réécrire le moteur ni remplacer son stockage.** La frontière intégrée est une UI React servie par Vite, une façade Python HTTP/SSE et `msr.control`/le protocole moteur existant. La liaison couvre à présent état, roster, archive, commandes de session et événements. Les tests automatisés vérifient les snapshots et le transport synthétique ; ils ne valident ni un shell Windows/WebView2, ni un LIVE TikTok ni l’enregistrement. Voir la section 5 et le rapport exhaustif pour les réserves, notamment l’import Tkinter du point d’entrée historique et l’absence de sécurité/packaging de production sur le host de développement. Si une commande/UI de production ne passe pas par le contrôle headless, compléter le contrat partagé plutôt que contourner ou dupliquer le moteur.

1. **Interface** : reprendre les pages React existantes et leurs styles/polices. Les pages n’importent que des types/commandes BTL, jamais les modules Python internes ni les chemins du disque.
2. **Hôte Windows local** : démarrer une seule instance du moteur, servir l’interface dans un shell desktop léger (évaluer WebView2 et sa disponibilité sur Windows 10), et fournir une petite façade native/Python. Cette façade lit/valide le fichier de contrôle local et appelle le protocole existant ; aucun secret/jeton moteur n’est envoyé au code de la page.
3. **Adaptateur de domaine** : transformer `channels` + `status` + événements en modèles BTL : créateur, état de contrôle, LIVE, enregistrement, erreur. Traduire les statuts avant de les afficher.
4. **Commandes** : `liste/ajout/suppression/activation/vérification`, `démarrage/pause/arrêt`, `réglages`, `liste/lecture/ouverture/suppression de vidéo`, `état disque`, notifications. Utiliser les commandes déjà présentes ; compléter le protocole/versionnement seulement si nécessaire.
5. **Événements** : employer `subscribe` (flux JSON d’événements) pour actualiser l’interface sans polling agressif ; conserver snapshot/status comme mécanisme de rattrapage après déconnexion. L’API actuelle autorise au plus huit abonnés, largement suffisant pour une seule interface, mais ce nombre n’est pas une limite de LIVE.
6. **Sécurité et disponibilité** : écoute loopback uniquement, port aléatoire et jeton conservés côté hôte, validation des chemins et arguments, reconnexion à l’événement, un seul moteur par dossier de données. Ne pas exposer un serveur backend sur le réseau local.
7. **Adaptation TikTok** : filtrer les plateformes au niveau du produit après inventaire des dépendances, garder `tiktok` dans le modèle/API, et garder les outils communs effectivement utilisés par TikTok. La bibliothèque pointe sur les fichiers réellement produits par le worker.

Avant l’implémentation, confirmer le choix du shell WebView2 et la stratégie d’emballage du moteur. Le protocole de contrôle TCP actuel n’est pas un serveur HTTP/CORS prêt à être exposé directement au navigateur ; l’hôte doit faire l’intermédiation.

## 5. Phases 4 à 6 — état et critères de sortie

La phase d’intégration a commencé sur la branche Arena à la demande de l’utilisateur. Les arbres du moteur et du frontend sont réunis dans le dépôt et le premier trajet réel UI/API/contrôle fonctionne sur données de test. Ce n’est pas une intégration complète : aucun connecteur non-TikTok n’a été retiré, le packaging n’existe pas et aucun LIVE n’a été capturé. Prochaines étapes :

- **Phase 4 (en cours) :** code source exporté sous `engine/` et `frontend/` avec commits identifiés ; état/roster/session/événements et archive raccordés. Continuer page par page : settings persistants, bibliothèque/actions, sécurité/contrat versionné, puis shell desktop ; ne supprimer des fixtures qu’après vérification de leur remplacement par des données moteur.
- **Phase 5 :** tests unitaires du contrat + tests simulés (aucune connexion réseau réelle supposée) ; puis essais TikTok réels, autorisés et reproductibles sur Windows : ajout/start-up en LIVE, notification, un puis plusieurs créateurs/flux, coupure/reprise/fin, arrêt propre, remux MP4 et lecture, reprise après arrêt brutal, fichiers et mesure CPU/RAM/bande passante/disque. Distinguer explicitement simulation et preuve réelle.
- **Phase 6 :** construire une application sans terminal, vérifier l’installation/désinstallation sous Windows 10 22H2, les notifications/tray, l’autostart, l’icône BTL, l’absence de suppression des vidéos personnelles et les dépendances sur une machine 6 Go RAM / disque mécanique. Ces validations ne peuvent pas être faites par le seul environnement Linux actuel.

**Ce plan est une liste de scénarios, pas encore un protocole de validation suffisant.** Il manque encore des critères pass/fail, les versions/outils de mesure, le volume/durée de chaque essai, la matrice de panne, l’instrumentation de synchronisation audio/vidéo et la procédure de collecte sans secrets. À compléter avant de déclarer le produit prêt :

1. **Contrat/bridge** : démarrage et arrêt idempotents ; versions incompatibles ; serveur absent ; token incorrect ; pertes/reprises d’événements ; état de rattrapage cohérent après reconnexion ; chaque action UI correspond à une commande moteur vérifiable.
2. **Roster/persistance** : identifiant valide/invalide, doublon avec/sans @ et URL, ajout/suppression pendant surveillance, pause/réactivation, erreur réseau conservée comme inconnue, redémarrage logiciel/Windows et migration du format historique.
3. **Enregistrement** : LIVE déjà démarré, démarrage pendant surveillance, fin naturelle, arrêt utilisateur, doublon d’événement, LIVE non accessible, coupure courte/longue, Streamlink absent/échec, changement de résolution, manque d’espace et disque retiré/remis ; vérifier l’absence de worker/processus orphelin.
4. **Fichiers** : pour chaque scénario applicable, vérifier fichier final avec ffprobe et lecteur Windows, codec/pistes audio et vidéo, durée, horodatage, dérive A/V sur des marqueurs mesurables, sidecar, noms/chemins sûrs, reprise TS après crash, et cohérence bibliothèque/fichier réel.
5. **Charge** : augmenter graduellement les créateurs surveillés puis les LIVE simultanés (sans plafond prédéfini), conserver la durée, charge réseau, CPU, RAM et débit disque, noter erreurs/taux de LIVE manqués et définir les seuils d’acceptation avec l’utilisateur. Ne pas extrapoler au-delà des essais.
6. **Windows/UI/distribution** : notifications sur poste configuré et minimisé, actions et suppression confirmées, tray et cycle fermer/minimiser/quitter, fonctionnement hors ligne avec polices embarquées, installation propre, mise à niveau/désinstallation, vidéos préservées, premier démarrage sans terminal et essais sur le PC cible.
7. **Régression/sécurité** : exécuter la suite complète du moteur et tests frontend/bridge ; vérifier redaction des cookies/URLs/tokens, autorisation locale, chemins, interruptions au cours d’une écriture et non-suppression automatique des enregistrements.

## 6. Audit du frontend et tests exécutés

Les constats de maquette ci-dessous décrivent le commit amont `frontend` avant intégration. La copie de travail actuelle a retiré ses tableaux fictifs et raccorde partiellement les données au moteur (voir sections 1, 4, 5 et rapport exhaustif).

- Pages observées : surveillance, créateurs, enregistrements, paramètres. Le thème sombre et les polices IBM Plex Sans / Sora / JetBrains Mono correspondent bien aux orientations de design.
- `src/lib/mock-data.ts` contient 8 comptes, 8 enregistrements, une activité, un espace disque inventé et les réglages d’exemple. `src/lib/app-store.tsx` met à jour ces exemples uniquement en mémoire et calcule durée/taille artificiellement.
- Les composants serveur `src/server/*.ts` sont des fichiers de commentaires sans implémentation. Dans l’interface, importer/exporter, ouvrir le dossier, choisir le dossier, sauvegarde/restauration n’ont que des toasts annonçant une disponibilité future ; les boutons de fenêtre du shell sont décoratifs.
- La page des créateurs n’affiche pas d’avatar récupéré (le composant génère une représentation locale) ; le statut réel et le lien de profil n’existent pas.
- La page d’enregistrements a un lecteur qui reçoit des métadonnées fictives au lieu d’un chemin exploitable. L’UI propose une limite de quatre simultanés qui doit disparaître, sauf décision ultérieure fondée sur mesure.
- Depuis l’import sous `frontend/` et les changements d’intégration : **4 tests Vitest réussis dans 2 fichiers**, `npx tsc --noEmit` et `npm run build` passent. L’installation npm a été faite avec `--legacy-peer-deps` ; deux vulnérabilités hautes sont signalées par npm audit. ESLint ciblé sur les fichiers modifiés : 0 erreur, un avertissement Fast Refresh. `npm run lint` complet reste en échec sur des erreurs de format Prettier dans le frontend importé (191 erreurs et 7 avertissements au dernier passage, y compris des fichiers non modifiés).

## 7. Décisions restantes pour la suite

La première tranche d’intégration est commencée. Les décisions techniques/produit restantes sont :

1. choisir et éprouver le shell desktop final (WebView2 ou autre), sans exposer le jeton moteur au frontend ;
2. préciser le classement BTL par créateur/date et sa migration, en préservant l’accès aux enregistrements existants ;
3. prioriser les prochains blocs : paramètres persistants, bibliothèque/actions sécurisées, notifications/tray, puis packaging Windows ;
4. définir le protocole/conditions d’essais sur Windows et le PC cible avant d’évaluer les capacités de détection et d’enregistrement.

Le plafond artificiel de quatre enregistrements a déjà été retiré de la maquette intégrée ; aucune capacité maximale mesurée ne lui est substituée.

La capacité réelle de plusieurs enregistrements TikTok et le comportement sur votre ordinateur Windows resteront « à tester », jamais présentés comme validés avant essais.
