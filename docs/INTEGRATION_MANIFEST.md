# Provenance et état de l’intégration BTL

## Copies de source

Les arbres des deux branches sont importés sur la branche Arena courante :

- moteur sous `engine/` : branche `engine`, commit `4e76f3fa3dcc7520396e819b35cca8a665c8f4ca` ; les modules du moteur n’ont pas été modifiés ;
- interface sous `frontend/` : branche `frontend`, commit source `ad213b8fb403dc6619a6eab8d64633710391167b`, avec les adaptations BTL décrites ci-dessous.

Les branches GitHub d’origine ne sont pas modifiées. Le prototype garde une copie `prototype/vendor/engine/` correspondant au snapshot qui a servi à son premier parcours ; le host d’intégration importe désormais `engine/` comme source canonique.

## Tranche d’intégration mise en place

- Ajout de l’adaptateur frontend `frontend/src/lib/backend.ts` : il lit l’état moteur et la bibliothèque par HTTP, transforme les lignes du roster en modèles BTL et conserve les états de vérification impossibles comme « état inconnu », distinct de « hors ligne ».
- `frontend/src/lib/app-store.tsx` utilise les snapshots de l’hôte pour le roster, les enregistrements, les enregistrements actifs, l’état de session, l’espace libre disponible et les événements SSE. Les erreurs/détails du contrôle sont affichés dans la liste des créateurs ; une vérification impossible reste « inconnue », pas « hors ligne ». Les données fictives du store ont été retirées. La page Enregistrements affiche les captures actives et permet de les arrêter via `record_stop`.
- Les actions créateur (ajout, activation/désactivation, retrait) et la demande de vérification immédiate appellent les routes locales, relayées aux commandes `msr.control`. Le démarrage/arrêt de session est également raccordé. L’ajout depuis l’interface active le créateur dans le roster, mais le moteur demeure en pause jusqu’à l’action explicite de démarrage.
- Les enregistrements finis sont lus depuis la commande d’archive moteur. La lecture vidéo HTML5 appelle une route locale qui ne sert qu’un MP4 déjà listé par l’archive et situé sous le dossier `streams_dir` configuré ; elle prend en charge les requêtes HTTP Range pour le seek. Le navigateur expose ses contrôles audio/vidéo natifs.
- La page Bibliothèque affiche aussi les totaux issus du scan réel, les lots en attente et le nombre d’éléments mis de côté. En filtrant un créateur, les métadonnées/titres et clips associés viennent de `recordings_browse`. La mise à l’écart passe d’abord par `library_plan`, puis l’action confirmée `library_execute` en mode réversible PendingDeletion ; les lots peuvent être restaurés par `library_restore`. La suppression définitive reste indisponible.
- L’ouverture du dossier Windows reste désactivée tant qu’elle n’est pas raccordée à l’hôte desktop.
- Les paramètres pris en charge sont lus depuis `config.ini` et enregistrés via `config_get`/`config_set` avec une liste blanche : fréquence de vérification, qualité réelle Streamlink/yt-dlp, modèle de nom, seuil d’espace libre, limites de partie, coupures sur résolution, fenêtres de reconnexion, dossier d’enregistrement et notifications UI/Windows. Les champs indiquent l’application immédiate ou au prochain worker. Le chemin est validé par le moteur et ne peut changer pendant une session. Les options Windows non prises en charge sont signalées au lieu d’être simulées. Aucun plafond artificiel d’enregistrements simultanés n’est exposé.
- Le host local surveille les événements moteur indépendamment du navigateur et, sous Windows, les relaie via Plyer vers les notifications système pour LIVE détecté/terminé, capture terminée, erreurs et espace disque faible. Il démarre aussi un contrôleur pystray : ouvrir l’interface, démarrer/arrêter la surveillance et quitter proprement. `--background` relance l’hôte via `pythonw.exe` dans un dossier de données persistant sous `%LOCALAPPDATA%`; le journal est écrit dans `btl-host.log`.
- Sous Windows, l’hôte sert `frontend/.output/public/_shell.html` et ses assets statiques depuis le serveur HTTP Python, puis ouvre la même origine dans `pywebview`/Edge WebView2. Le frontend est buildé avec `spa.enabled`; Node.js et `node_modules` sont nécessaires à la compilation, pas à l’exécution. Le paquet final doit inclure tout `frontend/.output/public`. `--dev-frontend` garde Vite comme choix explicite de développement. Si le tray est actif, réduire ou fermer masque la fenêtre et le menu tray la restaure. « Quitter » depuis le tray passe explicitement outre ce masquage, détruit la fenêtre et arrête l’hôte ; sans tray, une fermeture normale termine la fenêtre et le host. `--no-desktop` garde l’ouverture navigateur, toujours servie par le host. Le réglage moteur `GUI.notifications` coupe à la fois les toasts UI et Windows. L’endpoint `/api/notifications/test` et son bouton Paramètres permettent d’envoyer un toast manuel. Aucun faux événement de démonstration n’est notifié.
- Le démarrage Windows se règle dans Paramètres via `/api/windows/startup`. BTL crée ou retire un raccourci utilisateur dans le dossier Startup Windows (`WScript.Shell`/PowerShell), sans écrire dans le registre et sans privilèges administrateur. En source le raccourci lance `pythonw.exe`; en build PyInstaller il vise l’EXE gelé. Dans les deux cas, BTL utilise `%LOCALAPPDATA%\BoitierTiktokRecorder` par défaut (ou le dossier courant explicitement choisi), démarre dans le tray et laisse la surveillance arrêtée. Sur Windows, ce dossier est le défaut du host pour que roster et réglages survivent aux redémarrages.
- La première cible de runtime est définie comme un **ZIP portable Windows x64, PyInstaller onedir, Python 3.12 x64**, avec PyInstaller 6.22.3 épinglé. `packaging/windows/build.ps1` construit le shell SPA et le bundle ; `.github/workflows/windows-portable-package.yml` est le build Windows de vérification. `--package-smoke` démarre sous `spawn` un processus enfant qui importe le vrai `msr.worker.record_worker`, sans accès réseau ni capture. Ce format n’installe pas Python séparément et évite un MSI pour la première pré-distribution.
- `frontend/vite.config.ts` relaie `/api/*` vers l’hôte local via une URL relative côté navigateur. La liste `allowedHosts` comprend le sous-domaine `.e2b.app` pour la prévisualisation Arena.
- L’hôte dispose de routes pour l’état, l’archive, les paramètres en liste blanche, la bibliothèque, le roster, la vérification immédiate (refusée sans session), les commandes de session, l’arrêt d’un enregistrement, l’événement synthétique de test et SSE. `prototype/btl_vertical_host.py` démarre le moteur en pause, garde désactivées les chaînes non TikTok conservées dans le roster partagé, et ne lance pas le poller multi-plateforme ; l’API, les événements SSE et les notifications Windows sont limités aux créateurs TikTok. Le moteur et les modules communs restent intacts.

## Résultats de validation de cette tranche

- `npx tsc --noEmit` : réussi.
- `npm test` : **12 tests réussis** dans 2 fichiers (11 tests d’adaptation API + 1 test de routage), dont lecture de l’état de démarrage Windows et mise à jour du raccourci via le host.
- `npm run build` : réussi (client, SSR et sortie Nitro).
- ESLint ciblé sur les fichiers modifiés : **0 erreur**, un avertissement Fast Refresh existant/lié au provider.
- Test réel de la chaîne Vite → proxy → API Python → moteur : lecture d’état, ajout/lecture/retrait d’un créateur activé mais session tenue en pause, événement SSE synthétique ; le lanceur de frontend Windows simulé a aussi démarré Vite sur port disponible et validé `/api/settings` proxyé en HTTP 200.
- Smoke du host avec l’engine canonique : **50/50 assertions** au dernier passage, comprenant le service SPA, les statuts/autostart, le worker `spawn`, le précontrôle WebView2 simulé, le message d’outils manquants et le refus propre d’un port déjà utilisé. Aucune requête TikTok ni capture réelle ; l’événement reçu était synthétique. Le smoke utilise des shims temporaires pour les commandes de capture et ne valide ni les launchers frozen ni Windows.
- Validation frontend : `npm test` réussi (**12 tests**) ; `npm run build` réussi (client, SSR et Nitro) ; ESLint ciblé sans erreur. Ces vérifications et les doubles de test ne remplacent pas un essai sur Windows avec PowerShell, tray et WebView2 réels.

## Limites restantes — ce n’est pas l’intégration complète

- Le backend prototype reste un hôte local de développement, pas une API sécurisée/packagée pour production. Le shell WebView2 et le tray sont raccordés, mais leur fonctionnement réel reste à valider manuellement sous Windows. Le périmètre V1 accepté est le ZIP portable sans MSI; le sélecteur de dossier et l’import/export sont reportés. Le build Windows et le cycle automatisé install/update/uninstall ont réussi sur `windows-latest` au run [44922937660](https://github.com/Boitier13/Boitier_Tiktok_Recorder/actions/runs/44922937660); l’artefact ZIP candidat est disponible dans Actions.
- Le build PyInstaller et l’archive ZIP ont été exécutés avec succès dans le workflow Windows [44922937660](https://github.com/Boitier13/Boitier_Tiktok_Recorder/actions/runs/44922937660). Le run a passé les probes/`--package-smoke` et `test-lifecycle.ps1` (outils manquants, chemins avec espaces/accents, empreintes de données conservées, raccourcis et désinstallation sans purge). L’artefact ZIP candidat a été téléversé; ces tests automatisés ne valident ni Windows 10/11 sur postes réels, ni WebView2/tray/autostart réels, ni une capture TikTok. L’audit de redistribution et les notices complètes restent ouverts, donc le paquet n’est pas encore distribuable comme release. Aucun installateur MSI ni mise à jour automatique en ligne n’est inclus.
- Le frontend Windows sert les fichiers SPA produits par `npm run build` ; Node et `node_modules` ne sont plus requis à l’exécution, mais `frontend/.output/public` doit être inclus au paquet. `pywebview` et le runtime système WebView2 restent nécessaires à la fenêtre native.
- Aucun test sur Windows 10 ni toast réellement affiché, LIVE TikTok réel, capture/décodage d’un vrai média, piste audio/synchronisation A/V ou charge n’a été effectué. Le smoke utilise un faux adaptateur Plyer et des octets MP4 synthétiques pour vérifier le transport et la logique sans dépendre d’un poste Windows.
- Les fonctions non TikTok sont désactivées et masquées à la frontière BTL (roster, API, SSE, notifications) ; leurs modules spécifiques restent présents dans le moteur partagé et n’ont pas été supprimés afin de préserver le moteur canonique et ses dépendances communes.
- Tout le travail demeure sur `arena/8479bd6c-boitier-tiktok-recorder`; aucune branche supplémentaire n’est créée et aucune branche source n’est modifiée.
